# Data inventory (v2)

Everything the app can store, where it lives, and who can read it. This
is the source for the App Store Privacy Nutrition Label / Play Data
Safety answers when store listing time comes.

| Data | Where | Readable by | Notes |
|---|---|---|---|
| Answers (world/feed/test) | `v2_users/{uid}/answers` | **any signed-in user** | doc id = question id; one per question. The chosen option may be edited (D86, ≤1/min); the anchors snapshot and answer time are immutable, and each edit stamps `editedAt` |
| Learn first attempts (D32) | same subcollection, `learn-*` ids | any signed-in user | ONLY the first attempt per card ever reaches the server (create-only answers refuse retries); the scheduler's spaced retries stay in device localStorage (`insight.learn.v3`). No anchors snapshot. Feeds the exact "% got this right" aggregate; the server never stores which option is correct |
| Pulse answers (D139, roster D203) | same subcollection, `pulse-<name>_<YYYY-MM-DD>` ids | **any signed-in user** | One ordinal answer (1..5) per pulse per UTC day, create-only, day-keyed in the id itself — which is why a pulse id may never contain `_`: the rules parse the day off it. **Five pulses since D203** (pace · energy · sleep · focus · social), and two of them — sleep and energy — are why `docs/STORE-FORMS.md` answers Apple's **Health** row YES and `design/store/app-privacy.json` declares it collected and linked. Folds into `v2_question_aggs/{pulseId}_{day}` through the untouched trigger, so the crowd split is as public as any other answer's (D98). **Create-only** — the D86 edit arm's surface list keeps `pulse` out, so "you said what you said today" holds structurally. Erased with the account like every answer, and a pulse never asked writes nothing. **The CADENCE is not here and is not on the server at all**: how often someone wants to be asked lives only in device localStorage (`insight.pulseCadence.v1`, swept by the D51 purge). That is deliberate — a per-person rhythm for a health-adjacent question would be a new field, a new rules arm, a row here and a second store-forms conversation, and `dueOn()` needs none of it |
| Sealed duel answers (+ guess) | same, `g_{gid}_{day}` ids | **the owner only** | The one answer shape D98 did NOT publish, and the read rule is where that lives: the cross-user arm admits `surface in ["daily","feed","test","learn","pulse","call"]`, and a duel answer's surface is `group`/`duo`, so nobody but its author ever reads the document itself. What is public is the REVEAL written the next day (see below) — that is the seal, and it is timing rather than privacy. On a "pick" day the answer also snapshots the picked member's uid (`pickUid`, D224) — who the option index meant in the answering client's roster order — validated against membership at write time and carried into the reveal; it names a fellow member, which the reveal already does |
| Anchors snapshot | on each answer doc | any signed-in user | exact age **and** age band (D155 — both, not one instead of the other: the band is what the aggregate buckets on, since ~80 exact ages would blow `BREAKDOWN_MAX_BUCKETS`, while the age is what a screen naming a *person* prints — "Ceramicist, 29" reads as somebody, "Ceramicist, 25-34" reads as a cell; the birthday it is derived from still never leaves the device, and `firestore.rules` caps the field at three characters so a date cannot be smuggled through it), gender, country, city, education, profession, relationship, height band (D140 — a band select, never a centimetre field) — all optional, entered at account creation or in the profile's Basics card. Snapshotted at vote time so a later edit cannot move a past answer's cohort |
| Anchors (current) | `v2_users/{uid}.anchors` | any signed-in user | the editable copy the snapshot is taken from |
| Core test results | `v2_users/{uid}.testResults` | any signed-in user | Big Five, politics, values, social. **The politics result is special-category data under GDPR Art. 9** and since D98 it is readable like the rest of the profile — the old "never published, never leaves the owner doc" is retired, along with D44's carve-out on the political items themselves. Read across users since D112: the City constellation and its person card show a named person's axis scores beside yours — the person-to-person Compare read the D98 rules comment opened this field for. What is still true, and is a different claim: a test result is **never a breakdown dim** — it is not in the anchors snapshot, not in `BREAKDOWN_DIMS`, and no published cell is keyed by one, so the SERVER still never slices an aggregate by a result (D8). What is no longer true is the flat "nothing is ever cross-tabbed *by* it": since D146 the who-voted sheet's **Type cut** groups a question's cached voters by their matched **Big Five archetype** and draws each type's split. That is a CLIENT fold over two things that already publish (public answers, world-readable `testResults`) — it adds no read, no field and no cell, and exposes nothing a reader could not already have computed — but the app now performs and displays the cross-tab, so the disclosure says so (`web/privacy.html`, pinned by `check:policy-claims` — D183 moved the disclosures off `ui/LivePrivacyPanel`, which now prints only the blunt public-answers sentence). **Two different scopes since D202, and they are not the same claim.** GROUPING ANSWERS by an *instrument* is the Big Five only TODAY (the verified logic score — no instrument, no dims — also groups answers since D227; its own row below): politics, values and attachment do not group answers in the app, and **since D252 that scope is the app's current choice rather than a promise** — the "never used to group" sentence left `web/privacy.html` with its claims pin, on the owner's unwind-the-promises posture (D225's shape: an unneeded promise is a standing liability), so the page now describes what groups answers today and pledges nothing about tomorrow. The scope is still held in code by `data/typeSplit.SPLIT_TEST`, passed explicitly at every call site and pinned by its own test, so it cannot move by accident — widening it is a product decision with a page edit beside it, not a broken promise (D183 moved the disclosures off the in-app panel, so a citation to the panel copy is stale wherever it still appears). COUNTING PEOPLE by type widened at **D202** to all four instruments: the Mirror's type-mix card reads city, country or world through whichever system the reader picks, politics included. D157 §4 had refused exactly that, calling it "one parameter" away; the owner reversed it, `web/privacy.html` states the new reading rather than the old denial, and `check:policy-claims` pins the count-of-people disclosure (the never-grouped pin beside it retired with the promise, D252). `data/typeMix.TYPE_TEST` is now a default, not an enforcement point. Being a sample rather than a census, the cut states its own basis and withholds shares under `TYPE_SPLIT_SMALL`. Cross-user readers parse the field defensively (`data/similarity.ts`) because the rules validate only the key set. Place score profiles are computed from test *item* answer counts (rows below), never from this field. `web/privacy.html` and the store filing both state this in full |
| Verified logic score (D57) | `v2_users/{uid}.testResults.logic` | any signed-in user | Written only by the `logicSubmitV2` callable after server-side scoring — rules refuse client mutation (a client-writable copy would be forgeable). Carries marks, percentile (modelled until the anonymous histogram clears the D60 floor; measured — with the population size it was ranked against — after), and the server-observed attempt duration. **Per-item solve timings never leave the device** (they stay in `insight.logicTest.v1`); practice attempts send nothing at all. **Since D227 the who-voted sheet's Logic cut groups a question's cached voters by quarters of this percentile** — a client fold over two things that already publish (public answers, this world-readable field), the D146 type-cut shape: bounded sample, stated basis, the untested thin the basis and are never a band. Disclosed in `web/privacy.html`, pinned by `check:policy-claims`. Choosing not to take the logic test is choosing not to appear in this cut |
| Verified logic attempt | `v2_logic_attempts/{uid}` | nobody (server only) | One doc per account: seed, generator version, status, start/score times, per-day start counter. Holds the attempt's answer key (the seed) while open — which is why not even the owner may read it. Erased by `deleteAccount` |
| Logic score histogram + difficulty stats | `v2_logic_norms/{global,families}` (public mirrors); `v2_logic_norms_private/{global,families}` (exact) | any signed-in user (mirrors); nobody (exact) | 26 score buckets (0–25) + a count + the form length they belong to — no uid, no anchors, no timing. The `items` field starts a fresh era on any form-length change: 12-item scores never mix with 25-item ones (D61). Only the FIRST scored attempt per account counts (the D32 rule). The mirror is rewritten on every scored attempt with the same exact numbers the private doc holds — no floor and no cadence, the same as `v2_question_aggs` since D98. (The D60 floor is a different number that survives untouched: it gates whether the *percentile* is presented as measured or modelled, which is about statistical stability, not about who may read.) Survives account deletion: the count was never attributable to begin with. The `families` doc (D62) is the difficulty ledger: per rule-family seen/solved counts and per-slot solve counts from the same first attempts — **no timings** (per-item timings never leave the device; difficulty is learned from solve rates alone) |
| Test *item* answers | `v2_users/{uid}/answers/test-*` | any signed-in user; counts published exact | The individual cards the results above are computed from. They ship as ordinary feed cards (`surface: "test"`), so their **option counts** publish like any other question's. Since D98 the `test-political-*` items slice like every other family: D44's carve-out is reversed, so a political item's split by city and education publishes. The other test families (big5, values, attachment) always did — that is what the Mirror's cohort views read |
| Foresight verdicts (D126) | `v2_users/{uid}/foresight/{readId}` | any signed-in user | one row per call: `qid`, `dim`, `bucket`, `guess`, `answerIdx`, `n`, `at`. Create-only, owner-written, never updated or deleted — a prediction you can revise is not a prediction. `correct` is deliberately **not stored**: it is derived from `guess` and `answerIdx` by anyone reading, because a stored boolean would be an unfalsifiable claim about a computable fact. `answerIdx` — the slice's top option AT GUESS TIME — is frozen rather than recomputed, since a cell that says Yes today may say No next month and re-deriving would silently flip old verdicts. **Honest limit, recorded rather than papered over:** `answerIdx` is client-written, so a determined client can write a verdict matching whatever it guessed; the basis is published beside the claim, which makes the lie visible rather than impossible. Erased with the profile by phase 1b's recursive delete, asserted in `e2e-delete-account.mjs` |
| City confirmation (D205) | localStorage only (`insight.profileGeneral.v2`, `vitals.cityOk`) | this device | The city key the device's own location fix last agreed with — the difference between a city the phone confirmed and one somebody scrolled to. **Deliberately NOT an anchor**: `anchorsFrom` whitelists the nine keys it sends and this is not among them, so it never reaches the server. Its only job is local: a question that RATES a city writes `city: ""` on its answer when the phone has never agreed, so an unverified anchor takes no cell in the place scorecard (D187). Stored as the KEY rather than a flag, so re-picking a city invalidates it by comparison with nothing to clear. Swept by the D51 purge with the rest of the blob |
| Lens results | localStorage only (`insight.lenses.v1`) | this device | the nine minor instruments; deliberately not mirrored to the server (D8) |
| Feed memory | localStorage only (`insight.readRoom.v1`) | this device | one bit per answered question, drives the answer strip |
| Display name | `v2_users/{uid}` + `v2_groups.memberNames` | any signed-in user (D98); group members for the copy on the group doc | user-entered. Since D98 it is the label the whole app renders people under — shown beside every answer, not only in reveals. An account that sets none renders as "Someone" |
| Handle (D122) | `v2_users/{uid}.handle` + the registry `v2_handles/{handle}` | any signed-in user | user-chosen, 3–20 chars, unique. The registry is one doc per taken handle — id = the canonical form, holding the uid — so uniqueness is the DOCUMENT ID and needs no index. Server-written only (`claimHandleV2`): a claim is take-new-then-release-old in one transaction, which rules cannot express. **Readable by any signed-in user, and that is a real widening rather than a consequence of D98**: the rules permit only an exact-id lookup, so the registry answers "is @olaf someone" and never "who is everyone". This is the app's first ADDRESS — before it, two Annas were indistinguishable and no live search returned anyone. Released by `deleteAccount` phase 3b, which queries the registry by uid because the profile holding the name is already gone by then |
| People directory (D239) | `v2_people/{uid}` | any signed-in user | `name`, its lowercase `nameKey`, and the `handle` if one is claimed — nothing else, ever, because a row holding only what a result draws cannot leak a third field to a forgotten projection. Written by the owner (the client, on saving a display name) and by `claimHandleV2` for the handle, which stays immutable to the client the same way `v2_users.handle` does. **`nameKey` is rules-enforced to equal `name.lower()`** — not merely bounded — so what a person is found by and what the result shows are one string; without it a client could answer a search for "ada" with a row displaying "Bob". This is the app's first queryable directory and the exposure delta is **nil**: `v2_users` is world-read and therefore already listable, so every profile could already be enumerated — what changes is that finding one costs a prefix query instead of a sweep, and costs a small document instead of a whole profile. Erased by `deleteAccount` phase 3d, which needs its own arm because this is a top-level document keyed by uid and phase 1b's recursive delete of `v2_users/{uid}` does not reach it — the same trap the handle registry set in 3b |
| Circle invitations (D122) | `v2_groups/{gid}/invites/{invitedUid}` | **the invitee, and only the invitee** | `to`, `from`, `fromName`, `groupName`, `mode`, `at` — **no free text**. Server-written only; accepting is the sole path that appends to `memberUids`, which is the array the rules read to decide who may see a sealed duel answer. Anyone may invite anyone (D122), so an invite carries the inviter's handle and a circle name to someone who did not ask for either; it grants nothing until accepted, and `INVITES_PER_HOUR` is the defence against volume. Members deliberately cannot read the list — "who was asked and has not answered" is a fact about the invitee, and the membership `get()` that arm needed is a billed read the pulse tripwire caught. Erased both directions by `deleteAccount` phase 3c |
| Push tokens | `v2_users/{uid}/push/tokens` | **nobody** (`allow read, write: if false`); written only by the `registerPushToken` callable | native only; used for the single reveal notification. **Moved out of the profile doc at D98**: opening `v2_users` to every signed-in user would have published the fan-out list the reveal sender uses. Moved rather than re-guarded — a field guarded by a rule is one edit from being readable, a path with no read grant is not. The recursive delete of `v2_users/{uid}` still covers it |
| Group membership | `v2_groups/{gid}` | members | callable-managed; invite codes server-minted. Stays member-gated after D98 for a non-privacy reason: the doc carries `inviteCode`, which is a **capability** — a world-readable code would let anyone join any circle |
| Join requests (D240) | `v2_groups/{gid}.pending` + `.pendingNames` | members | who has asked to join and the name they asked under. **On the group document rather than in a subcollection**, and that is a cost decision: members already read this doc, while a subcollection would need a member-gated read rule whose only expression in Firestore is `get()` on the group — one billed read per request listed, the tripwire D122 backed out of for invitations. Server-written only (`requestJoinV2` / `approveJoinV2` / `declineJoinV2`); the sole member-writable field on this document is still `duoMode`, pinned by a rules test, because the queue is one hop from `memberUids`. Capped at `PENDING_CAP`, since a forwarded link lets a stranger lengthen it. Declining tells the asker nothing — the entry simply stops being there, on D122's reasoning that a "declined" state makes refusing somebody a message you have to send. Erased by `deleteAccount` phase 3c-bis, which needs its own arm because phase 1c matches on `memberUids` and a pending asker is by definition not in it |
| Follows (D101) | `v2_users/{uid}/following/{targetUid}` | any signed-in user | one-way, create-or-delete only, `to` pinned equal to the doc id. A follow is a bookmark, not a permission grant — it conveys no access D98 had not already given, so there is no request, acceptance or notification, and no pending state. The graph being world-readable is a recorded judgement call, not a consequence of D98, and reverses with one line in `firestore.rules`. `deleteAccount` sweeps both directions |
| Reveals | `v2_groups/{gid}/reveals/{day}` | **any signed-in user (D98)** | server-written; names + option picks for that day. Member-gated until D98, which retired the guarantee it was carrying: the votes inside a reveal are world answers' younger siblings, and "withholding the materialized copy while publishing the source would be a lock on a door with no wall". Here the source is NOT published — the sealed answers above are owner-only — so this document is the only public copy of a circle's day, and it is reachable by anyone holding the gid. What the reveal still buys is timing (written the day after play, which is what keeps the seal meaningful) and one read instead of N |
| Aggregates (public) | `v2_question_aggs` | any signed-in user | exact, published on every answer from the first one. **No floor and no cadence since D98** — `AGG_MIN_N`, `PUBLISH_EVERY`, complementary suppression and `tooSmall` are all gone, not paused (D81's pause was superseded rather than resumed). In a small cohort a count of 1 is readable as one person's answer, and the answer itself is public anyway. The document carries no per-vote timing — a count, not a log. **Since D226 it also carries `edits`** — a from→to count matrix of D86 answer edits, present only once a question has ever been edited. Moves, not people (one person editing twice is two cells), no uid, no timing; disclosed in `web/privacy.html` and pinned by `check:policy-claims`. Same erasure posture as the counts beside it: an anonymous tally, not attributable, so deletion does not unwind it |
| Per-anchor breakdowns | `v2_question_aggs.by` | any signed-in user | counts per cohort, exact per cell; never carries a name or a uid |
| Feed ads (D197) | `v2_ads/{id}` | any signed-in user; **written by nobody** (`allow write: if false`, seed only) | An ad CARD — advertiser, headline, body, an `until` window and at most one coarse audience tag. Not a question: it takes no answer, has no options, folds into no aggregate and has no answer arm anywhere in `firestore.rules`. **Holds nothing about anybody**, so there is nothing here for `deleteAccount` to erase and nothing an erasure could miss. The whole pool is world-readable on purpose: every device downloads it and decides locally which ad it matches (`data/sponsored.ts`), which is what keeps the server from ever being asked who should see what — the moment it were, a behavioural profile would exist whatever the intentions. Text only, and `check:content` refuses an image, a logo, a brand colour, a link and a tracking pixel BY NAME. No click-out, so no click to attribute and no impression to log |
| Graded Foresight CALLs (D194) | `v2_call_outcomes/{qid}` | any signed-in user; **written by nobody** (`allow write: if false`, admin SDK only) | The result of a tier-A call: `outcomeIdx` (the winning option, or `-1` for VOID), `resolvedAt`, `resolvedBy`, an optional `note`, and **`inputs` — the aggregate snapshot the grader actually read**. That last field is the collection's reason to exist in this shape: a resolved call is the one number in this app that is not a fold the reader can recompute, so the numbers it was computed FROM are published beside it and the device re-runs the same arithmetic on them (`data/callRubric.ts`, held byte-identical to the resolver's copy by `check:calls`). Carries no uid and nothing per-person — `inputs` is counts, the same counts `v2_question_aggs` already publishes — so there is nothing here for `deleteAccount` to erase; a leaving account's own call ANSWER goes with its other answers. The write deny is the sharpest line in the feature: a client-writable `outcomeIdx` would make every score forgeable in one request. Its mere existence is load-bearing too — `firestore.rules` refuses a call answer once the outcome exists, which is what stops a player reading a published grade and then "predicting" it |

**Not collected:** contacts, photos, free-text from strangers, advertising
or analytics identifiers, and any analytics SDK — the only third party is
still Sentry, crash-scoped. **Product analytics, stated precisely
(D268 → D270 → D271 → D272, the whole ladder):** the server *derives*
anonymous daily counts from answers already stored (the digest, D268);
the app *collects* one **anonymous, bucketed feature tally per sampled
device per day** (the attention shards, D270) which since D271 may carry
**per-question** seen/answered/skipped buckets — counts about questions
under an unlinkable label, never a person's reading list; and it collects
one **uid-keyed day rollup** (D272) — sessions, a foreground bracket,
quiet sessions, dayparts — readable by nobody including its owner,
carrying no question id by rules-enforced construction, TTL'd at 90 days
and erased with the account. **The ceiling above all of it is D269**, a
binding record: no event streams, no third-party analytics, no per-target
reads, no hesitation timing, no anchor or Art. 9 slicing, and the daily
and the Mirror never adapt to any of it. A future widening rewrites this
paragraph in the same PR, as every rung here did.

**Location — declare Coarse, and read why the old wording was wrong.**
This paragraph used to open "the v2 app asks for no location: the manifest
declares no location permission and nothing in `src/` writes one." Both
halves are now false, and this file is the audited list the store forms are
answered from — so the stale version produced an **under-declaration**,
which `docs/SHIP-CHECKLIST.md` correctly calls the direction that gets an
app pulled.

What is true today, after D9's amendment: `AndroidManifest.xml` declares
`ACCESS_COARSE_LOCATION` outright (plus `ACCESS_FINE_LOCATION` capped at
`maxSdkVersion="30"`, for the reason recorded beside it), `Info.plist`
carries `NSLocationWhenInUseUsageDescription`, and `src/v2/data/locate.ts`
calls `Geolocation.getCurrentPosition`. So: **Coarse location, linked to
user, App Functionality, optional.**

`Info.plist` also carries `NSLocationAlwaysAndWhenInUseUsageDescription`
since D107, and **it is not a declaration of anything.** Apple requires a
purpose string for every location API the *linked binary* names, and a
SwiftPM dependency of `@capacitor/geolocation` names
`requestAlwaysAuthorization` in a branch this app cannot reach — so the
string exists to satisfy that check and is a verbatim copy of the
when-in-use one. Nothing requests Always authorisation, no prompt for it
can appear, and `UIBackgroundModes` carries `remote-notification` only.
Read from this file and answer the store forms the same as before: no
background location, no location history. `npm run check:ios-location`
fails if any of that stops being true.

Declare it even though **no coordinate is ever transmitted** — the fix is
resolved to a city name on the device and discarded, so what leaves the
device is a city name. That is still coarse location data. Never tick
Precise: it is unobtainable by construction, not by policy.

**Sensitive info — read the precondition.** The retired v1
`insight_discoverable` documents carry a ~5km geohash alongside a Big Five
vector, political coordinates, age, gender, country and a free-text bio.
Client access to them is now closed (D4), which is not the same as them
being gone. **Declare sensitive personal info as "not collected" only
after the discoverable scrub has actually run** — the honest scope is the
whole document, not just its location field:

```bash
node scripts/scrub-v1-discoverable.mjs --project prvfire33          # report
node scripts/scrub-v1-discoverable.mjs --project prvfire33 --apply  # delete
```

Note that the v2 surface has its own Art. 9 answer regardless: the
politics test result is special-category data, so **Sensitive info stays a
real Yes** even once the scrub has run. The scrub changes the scope of the
claim, not the answer to that row.

**Deletion.** The `deleteAccount` callable wipes the profile, all answers,
group memberships, this user's votes and names inside shared reveals, the
rate-limit ledgers, the aggregate event ledger's entries naming them,
cross-user references (impressions they sent, relations naming them),
their takes and flags, the moderation queue's copy of any take of theirs,
and the auth user; it also purges every local `insight.*` key and the
offline cache on the device that ran it.

That queue copy is worth stating explicitly, because it is the one place a
user's words lived somewhere other than where they wrote them: the
moderation design copies a flagged take's text into `v2_mod_queue` so the
review run reads one collection and never the circle around it, and for a
while deleting the take did not delete the copy. It does now, and the
erasure e2e asserts it — including that someone else's queued take is left
alone.

Three things deliberately survive, and all belong on a store form:

- exact aggregate tallies. The counts themselves never name anyone,
  and the one record that could attribute them — the event ledger — is
  swept in the same call, so what survives is anonymous the moment the
  deletion returns. (One bounded exception: an answer still in flight
  through the trigger when the sweep runs can land its ledger entry
  afterwards; it self-erases at the 90-day TTL — D28.) And
- **the uid attached to any Sentry event already sent.** `deleteAccount`
  does not reach into Sentry, so those reports persist for the Sentry
  project's retention period. Only relevant if telemetry was on when a
  report went out — it is on (D76; since D211 there is no in-app switch,
  and only an opt-out recorded by an older build turns it off) — and
- **moderation verdict rows** (`v2_mod_verdicts`). They record that a take
  id was removed, kept or escalated, under which policy line, by which
  moderator — no author text, and no author uid in any field.
  **THE ID IS NOT NEUTRAL, and this paragraph used to say it was**: it
  claimed that once the take, the flags and the profile are gone "the id
  resolves to nothing". It does not. A world take's id is
  `{qid}_{authorUid}` and a reported face is `av_{uid}`, so for those two
  shapes the row retains a pseudonymous identifier of the moderated
  account — and, for a world take, the question they wrote under — after
  everything else about them is erased. A circle take's id is a Firestore
  auto-id and does resolve to nothing.
  Kept because the log is the audit trail the advisory phase's judgement is
  assessed from, and it is append-only by design. What the retention COSTS
  is the sentence above, stated accurately rather than assumed away.
  **Open, and the owner's call**: `web/privacy.html` says "Two things
  intentionally survive, and neither can identify you" and names the
  aggregates and the error reports. This is a third, and for two of the
  three take shapes the "neither can identify you" half does not hold. The
  fix is either a disclosure on that page or a change to how a verdict is
  keyed — the second trades the join the queue and the verdict share — and
  neither is a change to make unattended. Raised 2026-08-26.

retired in D4 and archived in `firestore.rules.v1-archive` — but they are
