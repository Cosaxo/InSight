fourth of the six lists (`PROGRAM-PLAN.md` §2.4, D352). A to-do item is
something a routine does; an owner item is something only the owner

- [ ] **`firestore.rules` is at Firestore's evaluation ceiling on the path every answer takes** — and the writes that hit it are refused, which is indistinguishable from the rule refusing them. Measured on `origin/main` @ 2398c1a7, 2026-09-04 20:05 UTC: one `npm run test:e2e` run emits *"Unable to evaluate the expression as the maximum of 1000 expressions to evaluate has been reached"* **ten times**, naming `create` @ `firestore.rules:1047` and `update` @ `:1109` (the `v2_answers` `allow create` and D86's `allow update` — named too, because a line number in prose has no gate behind it) — and the suite exits 0. `npm run test:rules` emits it **zero** times across 178 green tests, so the unit-level rules tests are unaffected and genuine (verified: widening the D86 edit-shape guard reds a case there). **Why it is the refusals that blow the budget, not the ordinary writes:** a legitimate answer matches the first branch of the create rule's `||` chain and short-circuits; a write that is none of the branches must evaluate every one of them, each with its own `keys().hasOnly([...])` and, for two, a `get()` on the question document. So the cost peak sits exactly on the writes that are supposed to be refused — eleven e2e cases assert a refusal and each of them is granted it by the budget running out rather than by the rule under test (`duplicate answer refused by rules`, `non-member cannot answer an open duel day`, `member cannot answer a day already revealed`, `learn retry refused`, `entity refused on a non-catalog question`, `optionIdx refused on a catalog question`, `optionIdx refused on a rank question`, `a second pulse answer for the same day refused`, `a wrong-size order refused by rules`, `duplicate ranking refused by rules`, `duel answers stay out of world aggregates`). **What it costs if it moves one clause further:** the ceiling is a hard Firestore service limit, not an emulator artifact, so a legitimate answer that crosses it is refused in production and the person loses the answer — silently, and looking exactly like a rule working. The ruleset went 1900 → 1937 lines on 2026-09-04 and the count did not move (measured: main's own rules produce the identical ten), so nothing recent caused this and nothing recent is safe to keep adding either. **Not fixed by a night shift, deliberately:** the repair is restructuring the answers create rule — cheapest discriminator first, or one branch per surface — in the file that guards every write in the app, and it wants a measurement of the expression count per branch that nothing in the repo produces today. Reproduction is one command: `npm run test:e2e` then `grep -c 'maximum of 1000 expressions'` on the output; it does not need a failing run, which is why four nights of reading only failures never found it. **THE MECHANISM, established 2026-09-05 — and it corrects this row's own earlier entry.** An hour earlier this row said the write SHAPE had been refuted as the cause, on the strength of a probe through `@firebase/rules-unit-testing` that produced no budget errors. **That was wrong, and the harness was the reason:** the unit harness does not reproduce this at all. Driven against the real emulator instead — auth+firestore only, no functions — the shape is exactly the cause, and it is one line to see:

        1  setDoc on a fresh document (create rule only) ....... ALLOWED
        2  setDoc over the EXISTING document ................... DENIED — ceiling
        3  updateDoc, legal D86 shape (update rule only) ....... ALLOWED
        4  updateDoc, illegal shape (update rule only) ......... DENIED — ordinary rule denial
        5  setDoc with merge:true over the existing document ... DENIED — ceiling
        6  setDoc on a fresh document again .................... ALLOWED

A `set` over an existing document makes Firestore evaluate `allow create` AND `allow update` in the same request, and the two together exceed the 1000-expression budget. Either one alone is comfortably under. Reproduced on the named database `insight` and on `(default)` alike, so the database is not the variable either. Row 5 is the one to look at: that is a LEGAL, intended D86 edit — moving your `optionIdx` — refused, purely because it was written with `setDoc(..., {merge:true})` rather than `updateDoc`.

**DOES THE APP DO THIS TODAY? No — checked, and this is why the row is a risk and not an incident.** The client edits with `updateDoc` (`editVote` in `src/v2/data/live.ts`) and only ever `setDoc`s an answer that does not exist yet. The offline queue is not a replay: `insight.pendingAnswers.v1` RECONCILES against the server on boot and rolls back, it does not re-issue the write. So no user is losing answers today. What the ceiling costs is the next change that writes an answer with `setDoc` over one already there — a retry, a merge write, an innocent refactor of one of the six `setDoc` answer paths in `live.ts` — which would fail as a PERMISSION DENIAL, looking exactly like a rule doing its job.

**AND ONE THING IS BROKEN TODAY, not merely at risk:** for a `setDoc` over an existing answer the rules never render a verdict at all — the budget is spent first (compare rows 2 and 5, ceiling, against row 4, an ordinary denial). Every e2e case that asserts a refusal by re-sending a whole answer is therefore asserting nothing about the rule it is named for; it would pass with that rule deleted. **Which is why this is a hidden ceiling and not a coverage hole, named so it can be checked:** `firestore-tests/rules.test.ts` pins these same guards genuinely and without hitting the budget — the duel-membership one at :2149 ("outsiders can't"), the reveal window at :698, the D86 edit shape at :1309, the rank and catalog bounds at :1398 and :1482. So no rule is unpinned; what is unpinned is the ceiling. *Source:* night shift B, 2026-09-04 and 2026-09-05; `firestore.rules:1047` and `:1109`.
